`^22.22.2 || ^24.15.0 || >=26.0.0` (validado com Node 22.23.1):

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-api.txt
python -m uvicorn src.api.app:app --reload --port 8000
```

No Windows, ative com `.venv\Scripts\Activate.ps1` em PowerShell. Não é
necessário configurar credenciais GLPI para esta demonstração.

Em outro terminal:

```bash
cd frontend
npm ci
npm run dev
```

8000. Para servir tudo pelo FastAPI, execute `npm run build` no frontend e
reinicie a API; abra `http://localhost:8000`.

## Jornadas para revisão

1. Escolha um técnico. Confira seu nome, a perspectiva `staff` e o aviso de
   simulação. Falhas e listas vazias têm nova tentativa de leitura.
2. Pergunte sobre **VPN**: a resposta mostra tipo, ID, título, referência e
   trecho das fontes. Referências textuais permanecem texto; apenas URLs
   absolutas HTTP/HTTPS viram links. HTML recebido é exibido como texto.
3. Escreva **impressora**. Uma opção de esclarecimento preenche o compositor;
   envie pelo chat. Enter envia e Shift+Enter preserva uma quebra de linha.
4. Uma pergunta sem palavra-chave gera **sem evidência**. **indisponível**
   simula **índice indisponível**, apresentado como uma situação diferente.
5. Escreva **abrir chamado** ou **adicionar acompanhamento**. A ação fica
   pendente e `preview_text` aparece exatamente como recebido, inclusive
   espaços e quebras de linha. Não há botões de decisão nesta entrega.
6. Digite **talvez**, **sim?** ou **sim, mas altere a prioridade**: nada é
   confirmado, a pendência permanece e o texto pode ser corrigido.
7. Digite **editar: descrição corrigida**. A nova prévia tem versão 2 e ainda
   exige outra confirmação. Digite **sim** para confirmar ou **não** para
   cancelar. Também são aceitos `confirmo`, `confirmar`, `cancelo`, `cancelar`,
   com ponto ou exclamação finais opcionais.
8. Use **abrir simular parcial** e confirme. O resultado parcial preserva o
   ID do chamado. **abrir simular incerto** exercita resultado incerto.
9. Crie outra prévia, troque de técnico e confira o contexto vazio. O
   contexto anterior e sua pendência são invalidados no backend, inclusive
   ao selecionar novamente o mesmo técnico. Respostas/erros atrasados não
   entram na conversa nova.
10. Recarregue a página com uma prévia pendente. O identificador da conversa
    é guardado em `sessionStorage`, e `getSession` recupera a pendência e o
    último desfecho disponíveis. O histórico anterior não é reconstruído.

Para falha de rede, interrompa a API ou use o modo offline das ferramentas
do navegador. O rascunho de mensagem/edição é preservado. Durante uma decisão,
a interface consulta a sessão antes de liberar outra tentativa e nunca
repete a operação automaticamente. Se a consulta falhar, o envio fica
bloqueado até **Consultar estado** concluir ou uma troca explícita ocorrer.
Confirmações antigas são apagadas para exigir uma decisão nova. Respostas
perdidas de edição são reconciliadas sem editar outra vez. Se o servidor
não fornecer pendência nem resultado, a interface informa essa limitação e
pede conferência antes de repetir. Uma sessão 404 pede novo contexto.

Os testes controlados também exercitam `stale_action_version`: carregam a
prévia atual com `getSession`, limpam a confirmação antiga e exigem outra
decisão sobre a nova versão. O texto da decisão usa sempre `/decisions`
com o `action_id` e a `version` que estavam apresentados; não usa `/messages`
para resolver a versão corrente no servidor.

## Extensões de contrato e sessões

- Nova rota `POST /api/sessions/{thread_id}/switch`, corpo `{character_id}`,
  retorna `SessionInfo`. Valida o personagem antes da troca; falha de validação
  mantém o contexto anterior. A troca bem-sucedida invalida o anterior.
- `SessionInfo.last_write_result` é opcional, com valor padrão `null`. Contém
  o último `write_result` disponível naquela sessão, sem histórico completo.
- As rotas/campos anteriores continuam presentes. A rota legada `/messages`
  ainda aceita confirmação simples para compatibilidade, mas agora rejeita
  perguntas ou combinações ambíguas como `sim?` e `s.i.m`.
- O mock reutiliza `SessionService.start/switch/set_pending/clear_pending`
  com um diretório **fictício** para os IDs 101/102. A credencial interna da
  SES-01 permanece no servidor e nunca aparece na resposta HTTP. Nenhuma
  listagem real de usuários GLPI foi executada nesta task.
- O mock atual continua sem autenticação HTTP por cookie: `thread_id` é o
  localizador do contexto de demonstração. O adaptador real deverá ligar os
  métodos à credencial de sessão HttpOnly e ao vínculo de `resume`, conforme
  SES-01, em vez de autorizar pelo identificador recebido do navegador.

## Limites e próximas integrações

- **SES-02:** autorização de ferramentas/alvos. O navegador não decide
  papel ou permissões. A ligação HTTP com as sessões reais da SES-01 ainda
  deverá ser feita no adaptador integrado, conforme descrito acima.
- **EST-01:** persistência durável, histórico e retomada após reinício.
  Reiniciar o mock perde sessões, pendências e resultados. `sessionStorage`
  guarda somente o localizador público da conversa na aba.
- **RAG-01:** conectar o agente, fontes e recuperação reais ao `ChatBackend`.
  As palavras-chave do mock apenas exercitam estados; não são roteamento
  inteligente nem prova de recuperação/Gemini.
- **ACO-03/04:** botões definitivos, registro de execução, idempotência e
  reconciliação com gravações reais. A UI mostra espera pela resposta HTTP;
  não inventa estados internos de execução que a API ainda não publica.

`partial`/`uncertain`, fontes e respostas são simulações explícitas. A
integração efetiva aqui é frontend → FastAPI mock → SES-01 com diretório
fictício; não houve ensaio com GLPI, índice, Gemini ou escrita real.
